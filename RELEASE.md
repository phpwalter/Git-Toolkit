## 1. 🎯 Purpose

This document defines the formal release criteria, validation flow, delivery format, and governance for Git Toolkit releases. It ensures traceability between project goals, technical readiness, and contributor transparency, serving as the **final gate to public tagging and distribution.**

---

## 2. 🚀 Release Criteria

Git Toolkit is eligible for release **only when all of the following conditions are met**:

| Category         | Criteria                                                                                               |
|------------------|--------------------------------------------------------------------------------------------------------|
| ✅ Milestones     | Relevant milestones (e.g., from [MILESTONES.md](./MILESTONES.md)) are complete and marked `Done`.       |
| ✅ Test Suite     | ≥ 80% test coverage; all automated tests pass consistently.                                            |
| ✅ CLI & Config   | All new CLI commands and configuration options are functional and documented.                          |
| ✅ Documentation  | `README.md`, `CONTRIBUTING.md`, and relevant `docs/` are up-to-date and accurate.                     |
| ✅ CI/CD          | All GitHub Actions workflows (CI, Release) are green on the `main` branch.                             |
| ✅ Security       | No critical or high-severity vulnerabilities reported by automated scans or private disclosures.       |
| ✅ Artifacts      | All required release artifacts are generated and available (see Section 3).                            |
| ✅ Code Quality   | Code adheres to project style guidelines (e.g., `black`, `flake8`) and passes linting checks.          |

---

## 3. 🧾 Release Artifacts

| Artifact           | Format / Access Point                                  |
|--------------------|--------------------------------------------------------|
| Python Package     | PyPI package (`git-toolkit`)                           |
| GitHub Release     | Tag (e.g., `v0.1.0`) with changelog and release notes. |
| Documentation      | `README.md`, `docs/` directory.                        |
| Change History     | `CHANGELOG.md` (generated by `semantic-release`).      |
| Test Report        | CI/CD pipeline logs and coverage reports.              |

---

## 4. 🧪 Versioning Strategy

Git Toolkit uses **Semantic Versioning (`MAJOR.MINOR.PATCH`)** as enforced by `semantic-release`:

| Level | Criteria                                                              |
|-------|-----------------------------------------------------------------------|
| MAJOR | Incompatible API changes, significant architectural shifts.           |
| MINOR | Backward-compatible new features, significant enhancements.           |
| PATCH | Backward-compatible bug fixes, performance improvements, documentation updates. |

The version number is automatically determined by `semantic-release` based on commit message conventions.

## 5. 📦 Delivery Channels

| Target          | Method                                                        |
|-----------------|---------------------------------------------------------------|
| GitHub Releases | Tags with attached changelog and release notes.               |
| PyPI            | Automated publication of the Python package.                  |
| Internal Teams  | Communication via project channels (e.g., Slack, internal docs). |

---

## 6. 🔁 Post-Release Process

### Bug Reporting

*   All issues should be filed via GitHub Issues.
*   Triage within 2-3 business days by Project Maintainer.

### Patch Releases

*   Issued as `vX.Y.Z` for critical bug fixes or security patches.
*   Triggered by specific commit message types (e.g., `fix:`).

### Feature Deferral

*   Features not included in a release are deferred to the [ROADMAP.md](./ROADMAP.md) or future milestones.

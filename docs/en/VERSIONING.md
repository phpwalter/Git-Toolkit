# Versioning and Release Policy

Git Toolkit follows Semantic Versioning.

## Authoritative version

`git_toolkit/version.py` is the authoritative runtime/package version source. Build and release automation must derive from that value rather than maintaining independent version strings.

## Version meaning

- MAJOR: incompatible configuration, CLI, plugin API, policy, or runtime behavior changes.
- MINOR: backward-compatible functionality.
- PATCH: backward-compatible fixes.
- Development builds use PEP 440 development versions such as `0.9.0.dev0`.

## Release invariant

For every production release, all of the following must identify the same version and source commit:

1. `git_toolkit.version.__version__`
2. Git tag `v<version>`
3. wheel/sdist metadata
4. GitHub Release
5. changelog release heading
6. PyPI release

A mismatch is a hard release failure.

## Release source

Only a green commit on `main` may be tagged for release. Feature branches, pull-request merge refs, dirty worktrees, and locally modified package files are not valid release sources.

## Automation

Release automation validates the tag/version identity before building. Publishing occurs from immutable build artifacts generated by the same workflow run.

## Pre-1.0 transition

The current development line remains `0.9.0.dev0` until all 1.0 release gates are satisfied. The version becomes `1.0.0` only in the final release-cut change after integration, not on individual feature branches.
